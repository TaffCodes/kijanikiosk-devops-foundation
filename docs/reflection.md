# Capstone Technical Reflection

## 1. What Did You Get Wrong?
During the initial design of the multi-environment Kubernetes deployment (`k8s/kk-payments-deployment.yaml`), I initially configured the staging and production differences by maintaining two separate Deployment YAML files (`kk-payments-deployment-staging.yaml` and `kk-payments-deployment-prod.yaml`) with hardcoded `namespace:` fields and inline `env:` blocks. That technical decision was wrong because maintaining duplicate Deployment manifests introduces configuration drift—if an engineer updates a resource limit, probe timeout, or image tag in staging but forgets to copy that exact line to the production YAML, staging smoke tests no longer validate the actual production specification. A much better approach—which I refactored into the final architecture—was stripping all environment-specific fields and namespace declarations out of `k8s/kk-payments-deployment.yaml` and injecting environment values exclusively via `envFrom` referencing `kk-payments-config`. This guarantees 100% manifest parity between `kijani-staging` and `default`.

## 2. Most Important Thing Learned
The most important concept I learned was **decoupling immutable artifact promotion from environment configuration using versioned tags and ConfigMaps**, introduced in **Week 8 and expanded in Week 9**. Earlier in the course, I viewed a deployment pipeline as a build script that recompiles code or edits manifest files for each target server. When we transitioned from VM-based blue/green scripts in Week 8 to Kubernetes ConfigMaps in Week 9, my engineering mental model shifted completely: a container image (`localhost:5000/kk-payments:1.0.0`) and its `Deployment` manifest must be built once as immutable artifacts, while environment identity (`DB_HOST`, `RECEIPT_BUCKET`) belongs strictly to the target namespace's runtime layer. That realization directly shaped this capstone's Jenkins pipeline, allowing the production stage to promote the exact binary and manifest verified in `kijani-staging` without rebuilding.

## 3. What Would You Do on a Second Pass?
If given a second pass on this specific system, I would make three component-specific changes:
1. **Replace HostPath Receipt Storage with an In-Cluster MinIO S3 Gateway:** Remove the `s3-receipts-volume` Kubernetes `hostPath` mount in `k8s/kk-payments-deployment.yaml` and deploy a dedicated MinIO StatefulSet inside the cluster so `kk-payments` writes receipts to `kk-payments-receipts-staging` over authenticated S3 HTTP APIs rather than shared node directories.
2. **Add Kubernetes NetworkPolicies in Terraform:** Expand `terraform/main.tf` to provision a `kubernetes_network_policy` resource inside `kijani-staging` that explicitly blocks cross-namespace pod traffic between `kijani-staging` and `default`.
3. **Add Automated Alertmanager Webhook Rollback:** Extend `prometheus/alert-rules.yml` with an Alertmanager webhook receiver that automatically triggers `kubectl rollout undo deployment/kk-payments -n default` whenever `KkPaymentsHighErrorRate` fires in production.
