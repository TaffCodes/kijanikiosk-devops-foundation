# Engineering Reflection and Systems Thinking

## 1. The /proc boundary
The `/proc` directory is not a traditional filesystem stored on a hard drive; it is a pseudo-filesystem (or virtual filesystem) created dynamically in RAM by the Linux kernel. Because it exists entirely in memory, its contents do not persist after a reboot. Instead, it acts as a real-time interface into the kernel's internal data structures and the state of active processes. When I ran `ps aux`, the command wasn't reading a static log file on disk; it was querying these dynamic, in-memory structures maintained by the kernel. This tells me that the data I was looking at during the investigation was a live, ephemeral snapshot of the system's exact state at that very millisecond, requiring real-time observation rather than post-mortem disk forensic analysis.

## 2. Kernel space and process isolation
A runaway user-space process cannot corrupt kernel memory because modern Linux operating systems strictly enforce privilege separation (protection rings) and virtual memory management. The kernel operates in a highly privileged state (kernel space), while applications like the rogue Python memory consumer run in a restricted state (user space). The CPU's Memory Management Unit (MMU), coordinated by the kernel, assigns each user process its own isolated virtual address space. If a process attempts to access memory outside its allocated boundary or tries to write directly to kernel memory, the hardware triggers a segmentation fault, and the kernel immediately terminates the process. If this boundary did not exist, a single memory leak, bug, or malicious script in any user application could overwrite critical kernel data structures, leading to immediate system-wide kernel panics, total system crashes, or severe security compromises.

## 3. The triage pipeline you built
During log analysis, I utilized the following pipeline to count error frequencies: `grep -E "ERROR|WARN" /var/log/kijanikiosk/app.log | awk '{print $4}' | sort | uniq -c | sort -rn`.
1. `grep` filters the raw log file, producing a stream of only lines containing the specified severity keywords.
2. `awk '{print $4}'` takes that stream and extracts only the 4th column (the specific error message or component), discarding timestamps and log levels.
3. The first `sort` organizes these extracted messages alphabetically, grouping identical strings together.
4. `uniq -c` counts the adjacent identical lines, outputting a list of unique messages prefixed by their occurrence count.
5. Finally, `sort -rn` sorts this counted list numerically in reverse, placing the most frequent errors at the top.
If I reversed the order of `sort` and `uniq -c`, the pipeline would break. The `uniq` command only collapses *adjacent* duplicate lines. Without sorting alphabetically first, identical errors scattered chronologically wouldn't be grouped, causing `uniq -c` to count them as separate instances and rendering the frequency analysis useless.

## 4. Containers and the kernel
A Docker container running on the investigation host would appear in the host's `ps aux` output because containers do not run their own independent operating system kernels. Unlike a Virtual Machine that uses a hypervisor to emulate hardware and run a separate guest OS, a container is simply a standard Linux process running directly on the host's kernel. The host kernel has absolute visibility into every process it schedules.
The "isolation" a container provides is an illusion created by Linux kernel features, primarily Namespaces and Control Groups (cgroups). Namespaces restrict what a process can *see* (giving it a private view of the filesystem, network stack, and process IDs), meaning the container thinks it is the only thing running. Cgroups restrict what a process can *use* (limiting CPU, memory, and disk I/O). Therefore, while the container is sandboxed, to the host operating system, it remains just another process on the tree.

## 5. Operational consequence
Based on the log evidence, the latency degradation was the result of a cascading failure originating at the database layer. The sequence began with the database connection pool reaching capacity limits (85% to 94%) between 03:45 and 04:01. By 04:07, the connection pool was entirely exhausted. Because no new connections were available, incoming API requests were forced into a queue. At 04:08, these queued queries hit their 30-second execution limits, resulting in mass timeouts.
This massive backlog of stalled Node.js event loops tied up application resources, causing the P95 latency to spike to ~480ms and triggering an application memory usage warning at 04:09. This application-level memory pressure was severely compounded by the unrelated rogue Python process consuming ~500MB of RAM, leaving the system highly constrained. Ultimately, the degraded database layer crashed or dropped all connections entirely at 06:22 (`ECONNREFUSED`), turning the latency degradation into a complete API failure.
